# 文档与实验发布规范

这份规范用于保持 TrainScale Lab 既适合初学者，又能经得住工程复核。它不要求所有页面
使用完全相同的模板，但要求读者始终能区分知识、操作、证据和边界。

## 四类文档各自做什么

| 类型 | 回答的问题 | 必须包含 |
|---|---|---|
| 模块 README | 这一章为什么学、从哪里开始 | 目标、状态、源码地图、最短路径、边界 |
| 实验设计 | 怎样公平地验证一个问题 | 预测、控制变量、correctness、指标、重复、停止条件 |
| 最终报告 | 结果说明了什么 | 代表值、机制解释、一般规律对照、反例和适用范围 |
| 操作教程 | 新手怎样无障碍复现 | 命令所在环境、前置检查、预期输出、失败恢复、结果下载 |

不要在 README 复制整份 raw JSON，也不要让最终报告变成命令日志。大文件由校验归档保存，
Git 只跟踪可读报告、配置和紧凑机器摘要。

## 每个实验的教学闭环

```text
问题 → 必要概念 → 运行前预测 → 最小实现 → correctness gate
    → 固定协议测量 → profiler/通信解释 → 单变量复测
    → 与一般规律对照 → 边界与下一步
```

“一般规律”用于帮助迁移，例如小消息受启动延迟支配、Amdahl 定律限制 strong scaling、
FSDP 降低分片状态但增加 AllGather/ReduceScatter。它不能覆盖实测；当实测与直觉不同，先检查
指标、负载和环境，再把差异写成学习内容。

## 结果发布分层

1. `raw/`：命令、stdout/stderr、rank JSON、checkpoint、trace；Git 忽略。
2. 校验归档：完整 raw 树、`SHA256SUMS` 和外层 SHA-256；供复核和长期保存。
3. 正式 artifact：runner 自动生成，包含 provenance、config、correctness、metrics 和 raw hash。
4. `*_final_summary.json`：人工审阅后从正式 artifact 提取的紧凑公开摘要，不替代 raw。
5. `*_final_report.md`：解释知识与边界，不手工发明 artifact 中不存在的数字。

失败结果不能被覆盖或删除后假装没有发生。重复下载、临时解压目录和确认无引用的错误副本可以
清理；唯一的 raw evidence 必须先归档并校验。

## 状态和措辞

- 实现状态使用“未开始、进行中、已完成、阻塞”；硬件或能力不存在使用 `unavailable`。
- `correctness=passed` 与 measurement quality 分开；波动过大时可以完成实验，但不能给出高精度结论。
- “观察到”只描述当前环境；“一般而言”必须说明机制；“推荐”必须给适用条件。
- 不使用单次最快值，不跨不同主机混合绝对吞吐排名，不把 profiler 时间当正式 benchmark。

## 新手命令规范

- 明确命令运行在 PowerShell、WSL/Linux Terminal 还是 JupyterLab Terminal；
- 第一次出现环境变量、反斜杠续行、退出码和目录归档时解释含义；
- 命令应可从仓库根目录复制执行，输出目录不得依赖作者机器；
- 写出成功时应看到什么，也写出何时停止而不是继续付费重跑；
- 云端教程必须包含下载哈希校验和真正关机/释放实例的步骤。

## 发布前检查

- 本地 Markdown 链接可解析，README 状态与验收清单一致；
- JSON 能解析，代码通过 ruff 和相应 CPU tests；GPU tests 引用已校验归档；
- 版本、硬件、commit、重复次数和指标单位齐全；
- 每个速度结论前有 correctness，每个机制结论有 profiler/通信证据；
- 明确哪些数字可迁移、哪些只是参考机器上的观测。
